# Releasing

## One-time setup (repository owner)

1. **Variable `RELEASE_TAGGER_EMAIL`**: the e-mail of the signing key used for release tags
   (Settings → Secrets and variables → Actions → Variables). The workflow refuses any tag not signed by it.
2. **Environment `release`** (Settings → Environments) with *Required reviewers*: nothing is published until a human approves the `publish` job.
3. **Tag signing**: configure git to sign (`git config user.signingkey …`; SSH signing works) and add the
   public key to GitHub as a *signing key* so tags show as *Verified*.
4. **Branch protection / ruleset on `main`**: require the `CI` checks, block force pushes, and restrict who can create `v*` tags.
5. *(optional)* **Apple signing secrets** for notarized macOS builds: `MACOS_CERTIFICATE_P12_BASE64`,
   `MACOS_CERTIFICATE_PASSWORD`, `MACOS_SIGN_IDENTITY`, `NOTARY_APPLE_ID`, `NOTARY_TEAM_ID`, `NOTARY_PASSWORD`.
   Without them the macOS build is ad-hoc signed and the release notes say so.

## Cutting a release

```sh
tools/release.sh 0.2.0 --dry-run     # every check, changes nothing
tools/release.sh 0.2.0               # bump, commit "Release v0.2.0", signed tag; never pushes
git push origin main v0.2.0          # starts the release workflow
```

Use `0.2.0-rc.1` style versions for release candidates; they publish as GitHub pre-releases. A candidate is
never promoted: the final version is a fresh tag.

## What the workflow checks and produces

| Stage | What happens |
|---|---|
| `verify` | The tag is an annotated tag that GitHub verified, signed by `RELEASE_TAGGER_EMAIL`; its commit is on `main` and passed `CI`; the tag equals the version in `Cargo.toml`. |
| `build` ×6 | macOS arm64 + x64, Windows x64 + arm64, Linux x86_64 + aarch64. Pinned toolchain, `--locked`, **no build cache**, `SOURCE_DATE_EPOCH` and path remapping. Linux is built on Ubuntu 22.04 and `tools/check-glibc.py` enforces glibc ≤ 2.35. |
| `publish` | Needs approval of the `release` environment. `SHA256SUMS`, Sigstore build-provenance attestations for every file, the release itself. |

Artifacts: `.dmg` (macOS), `-setup.exe` and `.zip` (Windows), `.tar.gz` (Linux), `sbom.cdx.json`, `SHA256SUMS`.
The SBOM is generated by `tools/sbom.py` from `cargo metadata` and `Cargo.lock` (only crates that ship; hashes from the lockfile).

## Tooling

| Script | Purpose |
|---|---|
| `tools/release.sh` | checks, version bump, signed tag |
| `tools/bundle-macos.sh [triple]` | `put.io adder.app` |
| `tools/sign-macos.sh` | Developer ID signing + notarization (needs the secrets above) |
| `tools/make-dmg.sh` | disk image with `hdiutil` only |
| `tools/package-linux.sh` | reproducible tarball + install scripts |
| `tools/package-windows.sh` + `packaging/windows/putio-adder.iss` | zip and Inno Setup installer (per-user, registers as available handler) |
| `tools/make-icns.sh`, `tools/make-ico.py` | icons from `assets/icon/` |
| `tools/sbom.py`, `tools/check-glibc.py` | SBOM, glibc floor |
| `tools/probe-macos-intake.sh` | manual check that magnet links and files reach the app on macOS |
