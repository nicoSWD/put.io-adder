# Releasing

## One-time setup (repository owner)

1. **Environment `release`** (Settings → Environments) with *Required reviewers*: nothing is published until a human approves the `publish` job.
2. **Branch protection / ruleset on `master`**: require the `CI` checks, block force pushes, and restrict who can create `v*` tags.
3. *(optional)* **Apple signing secrets** for notarized macOS builds: `MACOS_CERTIFICATE_P12_BASE64`,
   `MACOS_CERTIFICATE_PASSWORD`, `MACOS_SIGN_IDENTITY` (the Developer ID Application certificate), and
   `ASC_KEY_P8_BASE64`, `ASC_KEY_ID`, `ASC_ISSUER_ID` (an App Store Connect API key, for `notarytool`).
   The app and the disk image are both signed, notarized and stapled (`tools/sign-macos.sh`).
   Without them the macOS build is ad-hoc signed and the release notes say so.

## Cutting a release

```sh
tools/release.sh 0.2.0 --dry-run     # every check, changes nothing
tools/release.sh 0.2.0               # bump, commit "Release v0.2.0", annotated tag; never pushes
git push origin master v0.2.0          # starts CI and the release workflow together
```

The `verify` job waits (up to 45 minutes) for `CI` on the tagged commit, so pushing the commit and the tag in one
go is fine. If you protect `master` with a "require status checks" ruleset, a direct push of the release commit is
blocked unless the maintainer is allowed to bypass it; either allow that, or push the release commit through a
pull request first and tag the merged commit.

Use `0.2.0-rc.1` style versions for release candidates; they publish as GitHub pre-releases. A candidate is
never promoted: the final version is a fresh tag.

## What the workflow checks and produces

| Stage | What happens |
|---|---|
| `verify` | The tag's commit is on `master` and passed `CI`; the tag equals the version in `Cargo.toml`. |
| `build` ×6 | macOS arm64 + x64 (Developer ID signed, notarized and stapled: app, then disk image), Windows x64 + arm64, Linux x86_64 + aarch64. Pinned toolchain, `--locked`, **no build cache**, `SOURCE_DATE_EPOCH` and path remapping. Linux is built on Ubuntu 22.04 and `tools/check-glibc.py` enforces glibc ≤ 2.35. |
| `publish` | Needs approval of the `release` environment. `SHA256SUMS`, Sigstore build-provenance attestations for every file, the release itself. |

Artifacts: `.dmg` and `.zip` (macOS: the zip is what the in-app updater downloads), `-setup.exe` and `.zip` (Windows),
`.tar.gz` (Linux), `sbom.cdx.json`, `SHA256SUMS`. The names and layouts of the zips and the tarball are a contract with
the in-app updater: see docs/updates.md before changing them.
The SBOM is generated by `tools/sbom.py` from `cargo metadata` and `Cargo.lock` (only crates that ship; hashes from the lockfile).

## Tooling

| Script | Purpose |
|---|---|
| `tools/release.sh` | checks, version bump, tag |
| `tools/bundle-macos.sh [triple]` | `put.io adder.app` |
| `tools/sign-macos.sh` | Developer ID signing, notarization and stapling of the macOS app and disk image (needs the secrets above) |
| `tools/make-dmg.sh` | disk image with `hdiutil` only |
| `tools/package-linux.sh` | reproducible tarball + install scripts |
| `tools/package-windows.sh` + `packaging/windows/putio-adder.iss` | zip and Inno Setup installer (per-user, registers as available handler) |
| `tools/make-app-icon.py`, `tools/prepare-logo.py` | one-off (Pillow): the light and dark app icons (all sizes) from the supplied magnet artwork, and the transparent in-app logos |
| `tools/make-icns.sh`, `tools/make-ico.py` | the static macOS `.icns` and Windows `.ico` from the light icon set (while running, the app switches to the dark icon with its theme) |
| `tools/sbom.py`, `tools/check-glibc.py` | SBOM, glibc floor |
| `tools/probe-macos-intake.sh` | manual check that magnet links and files reach the app on macOS |

## Known gaps

- `THIRD_PARTY.txt` lists crate names and licence expressions only. MIT and Apache-2.0 also ask for the licence and
  copyright texts to be distributed with binaries; generating them (for example with `cargo-about`) is still to do.
- The SBOM describes the workspace across all six targets, not one file per artifact.
- The Windows `.exe` has no embedded icon (the installer, shortcuts and window do); embedding it needs a resource step in `build.rs`.
- `hdiutil create` prints a deprecation notice on current macOS; it still works, and a `diskutil image` variant is the follow-up.

## Checking the in-app updater (manual, needs two releases)

1. Install release N from its zip/tarball/installer into a folder you own (not `Program Files`, not a disk image).
2. Publish release N+1. Within 6 hours (or after *Check for updates…*) the toolbar shows **Update now**.
3. Press it, wait for the progress pill to finish, press **Restart to finish**. The app must reopen as N+1
   (Preferences → About shows the version) and `.putio-adder-update` must be gone next to it after the start.
4. Repeat from a read-only location and from a development build: both must say why they cannot update and offer
   **View release**.

## Not verified yet

The Windows and Linux packaging, the Windows installer, notarization, the macOS update zip and the workflow itself
have not been run, and no update has been taken from a real GitHub release on any OS (only the unpacking, swapping and
relaunching logic is tested, with fixtures):
they need GitHub's runners (and Apple credentials). Do a `v0.1.0-rc.1` dry run first and check every artifact on
a real machine of each kind.
